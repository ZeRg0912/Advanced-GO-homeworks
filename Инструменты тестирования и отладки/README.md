## Задача
Вам необходимо разработать HTTP-сервис, который принимает длинные URL и возвращает короткие идентификаторы, а также выполняет обратное преобразование.

## Подробное описание задачи
1. Функциональные требования:
Сервис должен предоставлять два HTTP-эндпоинта:

2. POST /shorten - сокращение URL:
· принимает JSON: {“url”: “example.com.../long/path”};\
· возвращает JSON: {“short_url”: “abc123”, “original_url”: “example.com.../long/path”};\
· генерирует уникальный короткий идентификатор (6-8 символов).

3. GET /{short_url} - получение оригинального URL:
· принимает короткий идентификатор в пути;\
· возвращает HTTP 302 редирект на оригинальный URL;\
· при отсутствии URL возвращает 404.

4. Технические требования:
· Хранение данных в памяти (map).\
· Валидация входящих URL (должны быть корректными HTTP/HTTPS адресами).\
· Обработка ошибок (некорректный JSON, невалидный URL, отсутствующий short_url).\
· Генерация уникальных коротких идентификаторов.

5. Обязательные конструкции:
· Table-driven tests для тестирования бизнес-логики.\
· httptest для тестирования HTTP-обработчиков.\
· t.Run для организации под-тестов.\
· Покрытие тестами не менее 80% для бизнес-логики.

8. Пример table-driven теста:
```
func TestURLShortener_Shorten(t *testing.T) {
    tests := []struct {
        name    string
        url     string
        wantErr bool
    }{
        {"валидный HTTP URL", "http://example.com", false},
        {"валидный HTTPS URL", "https://google.com/search?q=test", false},
        {"невалидный URL", "not-a-url", true},
        {"пустая строка", "", true},
    }

    shortener := NewURLShortener()
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            shortID, err := shortener.Shorten(tt.url)
            if (err != nil) != tt.wantErr {
                t.Errorf("ошибка = %v, ожидали ошибку = %v", err, tt.wantErr)
                return
            }
            if !tt.wantErr && len(shortID) < 6 {
                t.Errorf("короткий ID слишком короткий: %s", shortID)
            }
        })
    }
}
```

## Критерии оценки задания:
«Зачёт»
· Приложение компилируется и запускается без ошибок.\
· Реализованы оба эндпоинта (POST /shorten и GET /{short_url}).\
· Написаны unit-тесты для бизнес-логики с использованием table-driven подхода.\
· Написаны тесты для HTTP-обработчиков с помощью httptest, покрывающие успешные сценарии и случаи с ошибками.\
· Все тесты успешно проходят (go test завершается без ошибок).\
· Покрытие кода бизнес-логики тестами не менее 80% (проверяется через go test -coverprofile=coverage.out).\
· Используются методы t.Run для организации под-тестов.\
· Код структурирован и читаем.

«На доработку»
· Проект не компилируется или содержит критические ошибки.\
· Реализован только один эндпоинт или они работают некорректно.\
· Отсутствуют тесты или они покрывают менее 80% бизнес-логики.\
· Не используется table-driven подход или httptest.\
· Тесты завершаются с ошибкой.\
· Отсутствует валидация входных данных.\
· Не обрабатываются ошибки HTTP-запросов.

«Незачёт» ставится в крайнем случае, если вы присылаете пустое или недоработанное задание во второй раз после отправки работы на доработку.
